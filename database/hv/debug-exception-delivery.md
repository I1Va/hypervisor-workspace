# #DB delivery: what is measured, and why TRAP/SINGLE_STEP/DBVM/INTERRUPT_SHADOW fire

Four VMAware vectors depend on a `#DB` reaching a user-mode handler:
`TRAP`, `SINGLE_STEP`, `INTERRUPT_SHADOW`, `DBVM`. All four score 100 on this
stand. This document records exactly what has been established about why.

## What the checks require

**TRAP** (`vmaware.hpp: trap()`) is the most specific. It sets `DR0 = stub + 14`
and sets `TF` via the stub (`pushfq / or [rsp], 0x10100 / popfq / cpuid`), runs
the stub, and at the `#DB` requires:

```c
constexpr u64 required_bits = (1ULL << 14) | 1ULL;   /* BS | B0 */
const u64 status = info->ContextRecord->Dr6;
if ((status & required_bits) != required_bits) { ... detection ... }
```

and exactly one hit (`if (hit_count != 1) hypervisor_caught = true;`).

**SINGLE_STEP** requires a genuine `EXCEPTION_SINGLE_STEP` at a CPUID.
**DBVM** uses ICEBP (`0xF1`) and additionally checks that guest RIP advanced.
**INTERRUPT_SHADOW** uses the stub in an interrupt shadow.

So the useful measurement is never "did an exception arrive" but **what exact
DR6 did the guest's handler see, and how many times**.

## Measured facts (boots 62-74, `tools/trapdb.cpp` and `tools/tfprobe.cpp`)

1. **TF is accepted.** A stub that sets TF with `popfq` and then reads RFLAGS
   back without clearing it returns `rflags = 0x306`, bit 8 set. TF survives.

2. **No trap is delivered to user mode with the exception bitmap at 0.**
   Every `#DB` class is swallowed: TF alone, DR0 alone, ICEBP, and TF across
   CPUID all produce `hits=0`. A 100-iteration loop under TF completes in full
   (`counter=100`), i.e. execution is not stopped at the first boundary.

3. **The processor does raise #DB.** With `#DB` intercepted (exception bitmap
   bit 1), a VM exit is taken with `reason 0`, vector 1, and
   `rflags = 0x306` - so the trap really is generated by the hardware.

4. **The processor does not update DR6 for an intercepted #DB.** Root-mode DR6
   at that exit reads `0xffff4ff0`, i.e. the reset value with BS set. So DR6 is
   entirely the VMM's responsibility in this configuration, not the hardware's.

5. **DR0-DR3 and DR7 are usable by user mode.** Writing `DR0=0x7FF6DEADB000`,
   `DR7=1` and reading back gives the same values (`DR7` reads `0x401`, the
   reserved bit plus LE0). So debug-register ownership is not the blocker.

6. **Re-injecting the intercepted #DB fails VM entry.** With interception
   enabled and `InjectInterrupt(HardwareException, Debug, ...)` used to forward
   it, the guest dies with `VM-exit reason (Full) = 80000021` (VM-entry failure,
   invalid guest state) followed by `PANIC`. The injection is malformed; this is
   a hypervisor bug, not a guest one.

## What this rules out

- Not a topology problem: `tools/topo2.cpp` shows 4 physical cores, no SMT, one
  NUMA node, correct L3 sharing, `GetActiveProcessorCount = 4`.
- Not a missing trap: the hardware raises `#DB` (fact 3).
- Not debug-register ownership: user mode owns DR0/DR7 (fact 5).
- Not `--percent` style early exit: these were measured per technique.

## What is still unknown

Why the natively-delivered `#DB` (bitmap 0) never reaches a user-mode handler,
given the hardware raises it and the registers are owned.

## What intercepting #DB actually does (second attempt, boots 6-16)

Enabling bit 1 after ExitBootServices and forwarding the trap was tried again
with three fixes: per-core arming, TF cleared on forward (as hardware does), and
the pending-debug field left clear. Results:

- The VM-entry failure at `0x80000021` **no longer occurs** - clearing TF on
  forward fixed that. The previous panic was a re-injection loop, not invalid
  state.
- But the guest still receives no exception, and `ICEBP` now **hangs** the guest.
- The `#DB` exits observed have `RFLAGS = 0x202` (TF **clear**) and no DR match,
  i.e. they are not the single-step trap being sought. They are later or
  unrelated debug exits.
- Stamping `BS` onto such an exit is wrong: it presents a single-step status for
  a trap that never happened, and Windows discards it as spurious. ICEBP must be
  recognised by its opcode (`0xF1` at guest RIP) instead of by assumption.

Conclusion: interception-based forwarding is **not** the fix. It converts a
detection into a hang, which is strictly worse. The experiment is reverted and
preserved at `/tmp/opencode/db_work_v2.patch`.

## Remaining candidates

1. **The kernel debugger.** `debug Yes` in `{current}`, and
   `KUSER_SHARED_DATA + 0x2D0` reads `0x310` (784), matching the documented
   `ActiveProcessorCount`, so the offsets are valid and `0x2D4` reads 1 -
   consistent with `KdDebuggerEnabled = 1`. An initialised KD is documented to
   consume `#DB` and own the debug registers, which fits every observation.
   **Not proven**: `0x2D5` reads 10 (not a boolean), so the layout is unconfirmed
   for this build, and both `bcdedit /debug {current} off` and
   `/set {current} debug No` report success but revert to `Yes` on the next boot,
   so it cannot be tested from inside the guest.

2. **The injection path** - fixed enough to stop panicking, but still does not
   deliver the trap.

## Next

1. Settle the KD question outside the guest. Nothing inside can answer it while
   the BCD entry is restored every boot.
2. If KD is not the cause, the trap is being discarded in the kernel's debug
   handler. That needs a different lever entirely: the `#DB` must arrive with a
   DR6 the handler accepts, and with bitmap 0 the hypervisor cannot influence it.
3. Do not re-attempt interception forwarding without a delivery mechanism that
   is proven not to hang on ICEBP.

## Residual risk

The `#DB` work is **not committed**. Patches are at
`/tmp/opencode/db_work.patch` (first attempt) and `/tmp/opencode/db_work_v2.patch`
(second attempt, panics fixed but ICEBP hangs). The committed baseline
(`037de0b`) is the stable one and leaves all four vectors at 100.
